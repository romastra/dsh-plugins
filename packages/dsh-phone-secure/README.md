# Защищённый доступ с телефона

Локальный HTTPS-вход к существующему DSH Desktop 0.2.2-rc.3 / rc.5. Отдельный экземпляр DSH, nginx, WSL, Docker и дополнительные программы не устанавливаются. Используются рантайм Node.js из DSH и штатные средства Windows PKI.

## Вход

После установки включите строку `secure-phone-lan` в Plugins: новый шлюз по умолчанию не открывает порт. Локальные каталоги по умолчанию берутся из DSH Home.

1. Один раз установите на Android открытый корневой сертификат `phone-access/phone-root-ca.cer` как **сертификат ЦС**. Сравните его SHA-256 с отпечатком на ноутбуке; не устанавливайте неподтверждённый сертификат.
2. На ноутбуке откройте `phone-access/connect.html`. Актуальный QR содержит HTTPS-ссылку с токеном DSH. Этот документ и QR дают полный доступ владельца, не пересылайте их другим.
3. Подключите телефон к той же доступной LAN, считайте QR и откройте полную ссылку в обычном Chrome. При проблеме встроенного сканера используйте «Копировать ссылку» и новую вкладку Chrome.
4. DSH выдаёт штатную подписанную cookie. Дополнительной cookie шлюза, IP-сессии и суточного таймера нет. Срок cookie задаёт DSH, по умолчанию 30 дней от выдачи; проверка каждого запроса сама по себе не продлевает срок.

Локальная ссылка для браузера ноутбука остаётся HTTP на loopback; Desktop и его транспорт не перенастраиваются. Телефон использует HTTPS на порту **63819**. Старый вход HTTP на 3080 после перехода закрывается; старые cookie для этого порта не подходят к новой authority. Смена порта сама по себе не отзывает URL-токен текущего процесса: после перехода нужно один раз перезапустить DSH, чтобы прежние HTTP-ссылки перестали подходить по токену. Обычный перезапуск меняет launch token, но не ключ подписи уже выданных cookie.

## Разные сети

Откройте **Настройки → Доступ с телефона** (пакет `@local/dsh-phone-settings`), выберите адаптер по имени/IP и нажмите «Применить и запустить». Шлюз возьмёт его IPv4, откроет TCP 63819, выпустит серверный сертификат и обновит ссылку и QR. Выбор GUID сохраняется штатным ConfigEditor и восстанавливается после перезапуска DSH; приватный каталог ЦС для настроек не используется.

В настройках показываются **все** адаптеры: физические, виртуальные, VPN, туннели, скрытые, отключённые и без IPv4. Нет фильтров по типу устройства, диапазону IP или наличию шлюза; для подключения пригодны в том числе публичные IPv4, 169.254.* и 127.*. В автоматическом режиме выбирается готовый адаптер с IPv4, с прежним предпочтением Wi-Fi/Ethernet. Явный выбор никогда не отбрасывается из-за виртуального типа. `interfaceGuid` закрепляет конкретный адаптер. Если он недоступен, вход закрывается без скрытого перехода на другую сеть; после возвращения адаптера восстанавливается автоматически. Повторное применение того же выбора запускает безопасную повторную проверку без ненужной замены работающего сертификата.

При смене выбранного IPv4 или подсети старый слушатель закрывается, для нового IP выпускается серверный сертификат от того же ЦС, затем обновляются HTTPS-вход и локальный QR. Повторно доверять корневому сертификату на телефоне не нужно. Но cookie со старой authority не переносится на новый IP: первый вход там выполняется по обновлённому QR.

Слежение за адресами выполняется внутри расширения; Планировщик Windows и отдельная служба ЦС не нужны. Поддерживается любой назначенный адаптеру одноадресный IPv4. Недоступный и IPv6-only адаптер остаётся в списке; выбранный GUID сохраняется, но шлюз ждёт IPv4. Изоляция клиентов в гостевой Wi-Fi-сети, запреты локального трафика VPN и недоступность устройств друг другу не обходятся. Из разных сетей одновременно этот локальный вход напрямую недоступен.

Шлюз привязывается точно к выбранному IP. Для VPN с локальным /32 нельзя вычислять разрешённых удалённых клиентов по этому префиксу: маршрутизируемый телефон допускается к штатной авторизации независимо от своей подсети. Host/Origin, TLS и проверка токена/cookie сохраняются на каждом запросе.


## Авторизация и граница доверия

Проверка выполняется перед **каждым** HTTP-запросом и перед открытием WebSocket, в том числе для favicon, HTML, JS/CSS, ресурсов плагинов и неизвестных путей. Самостоятельной проверки HMAC и копии ключа DSH нет: используется штатный `connection.authorizeIndex` и проверка живого внутреннего carrier через `requestRejection`.

Штатный `authorizeIndex` сам не проверяет Host/Origin и не различает успех/отказ одним boolean: успешный login возвращает false вместе с 303. Поэтому расширение отдельно строго проверяет внешний HTTPS Host, Origin, Sec-Fetch-Site, формат URL и состояние своего контекста, а положительным bootstrap считает только точную штатную ветку `GET /?token=...` с 303. Ошибки проверки остаются в памяти, не отправляются клиенту.

После полной внешней проверки проксирование идёт к фиксированному loopback-серверу DSH с каноническими внутренними Host/Origin и отдельной **штатной cookie DSH только в RAM**. Она выпускается самим DSH, никогда не передаётся наружу и не записывается в файлы. Это владелец-владелец bridge для обычного браузера; он не предоставляет анонимам Peer и не является публичным многопользовательским/API-remote шлюзом. Пользовательские Forwarded/X-Forwarded-* не создают доверия. Динамически менять trustedHosts основного DSH при каждом перемещении между сетями не требуется.

Нативные `dsh-auth-*` Set-Cookie от внутреннего proxy-ответа не выпускаются наружу; публичная cookie выдаётся только внешней веткой штатного bootstrap. На внешних cookie выставляется Secure. Любой 401/403 из внутреннего carrier дополнительно подавляется.

## Молчание и лимиты

При отказе не отправляются HTTP-статус, HTML/JSON, название, иконка или редирект. Подключение переводится в ожидание без дальнейшего проксирования и накопления тела. По умолчанию допускается до **10** таких соединений суммарно и до **3** от одного IP, удержание — не более **120 секунд**. Сверх бюджета соединение закрывается без HTTP-страницы. Разрешённые соединения не занимают этот бюджет; предусмотрены отдельные ограничения TLS/заголовков и общий аварийный предел.

После отказа HTTP/1.1 соединение карантинируется целиком: последующие pipelined-запросы по нему не исполняются. По возможности автоответы HTTP parser/Expect/тайм-аутов подавляются тем же входным слоем. TLS работает только с HTTP/1.1 и необходимым WebSocket upgrade, без HTTP/2/3.

Это не делает порт невидимым: TCP/TLS handshake, сертификат, TLS alerts на ошибках протокола и закрытие сверх лимита остаются наблюдаемыми. Страница ошибки самого Chrome и ранее сохранённые title/favicon/cache не являются ответами DSH. Против неограниченного DDoS гарантий доступности нет.

## Ключи и сертификаты

Корневой приватный CNG-ключ создаётся в защищённом хранилище текущего пользователя Windows как неэкспортируемый. На телефон передаётся только открытый сертификат ЦС. При выпуске серверного сертификата его зашифрованный PFX и пароль передаются между локальными процессами только в памяти, не через командную строку или журнал; временная leaf-запись удаляется после выпуска. Подмена или потеря сохранённого корневого ЦС не должна незаметно создавать новый — потребуется явное восстановление.

Установка своего ЦС — значимое доверие: владелец его ключа может подписывать сертификаты и для других сайтов. Не распространяйте ЦС, не экспортируйте корневой приватный ключ и удалите доверие на телефоне, когда функция больше не нужна. Обновление leaf не требует переустановки корня; истечение/замена корня требует.

## Отключение и диагностика

Выключите весь набор `@local/dsh-phone-secure` в управлении плагинами. Слушатель и ожидающие подключения закрываются; локальные секретные ссылки/QR заменяются сообщением об отключении. Корневой ЦС автоматически не удаляется, чтобы не разрушать доверие на телефоне без согласования.

`phone-access/gateway-status.json` содержит только несекретное состояние: выбранную сеть, чистый origin, срок сертификата и код ошибки. Токены, cookie, PFX и приватные ключи в него не записываются. При отсутствии IPv4 у выбранного адаптера или ошибке сертификата вход остаётся закрытым; отката на HTTP нет.
